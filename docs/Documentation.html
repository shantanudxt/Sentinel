Current Capabilities

What Sentinel Does

The platform provides a complete telemetry pipeline from ingestion to persistence with reliability guarantees.

Ingestion

REST API

FastAPI endpoint receives robot telemetry with Pydantic validation — range checks on temperature, vibration, and motor current.

Transport

Kafka Event Streaming

Asynchronous event processing through the robot-events topic with a dedicated consumer group for processing.

Reliability

Manual Offset Commits

Kafka offsets are committed only after successful database persistence, preventing message loss on DB failures.

Persistence

PostgreSQL Storage

Telemetry is persisted to the robot_telemetry table with transaction rollback on failure and queryable endpoints.

Testing

Robot Simulator

Synthetic telemetry generator for local development and testing, posting events every 5 seconds to the ingestion API.

Infrastructure

Docker Compose

Containerized environment for API, consumer, Kafka, and PostgreSQL with health checks and service dependencies.

All telemetry routes are prefixed with /api/v1. FastAPI auto-generates Swagger UI at /docs and ReDoc at /redoc.

Ingestion Flow

When POST /api/v1/telemetry receives a payload, it validates the structure via the RobotTelemetry Pydantic model, then calls publish_telemetry() to send the event to Kafka. If Kafka is unreachable, a 503 is returned with "Telemetry ingestion service unavailable". On success, the API returns 202-style acceptance with the robot ID.

Design Decisions

Architecture Choices

Two core decisions shape Sentinel's reliability model.

Decision 1

Manual Kafka Offset Management

Kafka offsets are committed only after successful database persistence. This prevents a message from being acknowledged before its telemetry has been stored.

Failure Path

If db.commit() raises, the transaction is rolled back and the offset is not committed — the message gets reprocessed on the next poll.

Decision 2

PostgreSQL for Persistence

PostgreSQL provides a reliable relational store for the current telemetry workload while keeping the architecture straightforward and easy to run locally.

  • robot_telemetry table with indexed robot_id
  • SQLAlchemy ORM with explicit session management
  • Auto-creates tables on API startup via init_db()
  • Schema is simple — ready for time-series DB migration later
Future-Proof

A specialized time-series database can be introduced as scale and query requirements evolve.

Configuration

Environment Variables

Sentinel uses pydantic-settings to load configuration from a .env file. Copy .env.example to .env and provide values.

Variable Default Description
POSTGRES_USER — PostgreSQL usernameRequired
POSTGRES_PASSWORD — PostgreSQL passwordRequired
POSTGRES_DB physicalai Database name
POSTGRES_HOST localhost PostgreSQL hostSet to postgres in Docker
POSTGRES_PORT 5432 PostgreSQL port
KAFKA_BOOTSTRAP_SERVERS localhost:9092 Kafka broker addressSet to kafka:9092 in Docker

Note

.env is excluded from version control. Use .env.example as the template. When running through Docker Compose, the API and consumer use Docker service names (postgres, kafka) for host resolution.

CI Pipeline

GitHub Actions runs pytest on Python 3.10 for every push to main and feature/** branches, and on all pull requests targeting main. Tests use an in-memory SQLite database and mock Kafka producers — no external services required.

Schema validation and schema registry integration for contract enforcement across producers and consumers.
