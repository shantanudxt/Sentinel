# Sentinel

**Industrial robotics telemetry ingestion platform built with FastAPI, Apache Kafka, and PostgreSQL.**

Sentinel demonstrates a reliable event-driven pipeline for receiving, transporting, and persisting telemetry generated by industrial robots. The project is designed around reliable message processing, explicit database transaction handling, and containerized local development.

[![CI](https://github.com/shantanudxt/Sentinel/actions/workflows/tests.yml/badge.svg)](https://github.com/shantanudxt/Sentinel/actions)

## Why Sentinel?

Industrial robots continuously generate telemetry such as temperature, vibration, and motor current. Sentinel provides a simple architecture for ingesting these events through Kafka and persisting them in PostgreSQL while ensuring that failed database operations do not result in acknowledged Kafka messages.

## Current Capabilities

* REST API for receiving robot telemetry
* Kafka-based asynchronous event processing
* Manual Kafka offset commits after successful database persistence
* Database rollback when persistence fails
* Synthetic robot telemetry simulator for local testing
* Docker Compose environment for API, Kafka, and PostgreSQL
* Automated tests and continuous integration

## Telemetry Event

Sentinel processes telemetry events with the following structure:

```json
{
  "robot_id": "ARM-001",
  "temperature": 72.5,
  "vibration": 0.04,
  "motor_current": 3.2,
  "timestamp": "2026-08-08T23:00:00Z"
}
```

The event is published to the `robot-events` Kafka topic and subsequently persisted to PostgreSQL.

## Design Decisions

### Manual Kafka Offset Management

Kafka offsets are committed only after successful database persistence. This prevents a message from being acknowledged before its telemetry has been successfully stored. If database persistence fails, the transaction is rolled back and the Kafka offset is not committed, allowing the message to be reprocessed.

### PostgreSQL for Persistence

PostgreSQL provides a reliable relational store for the current telemetry workload while keeping the architecture straightforward and easy to run locally. A specialized time-series database can be introduced later as the system's scale and query requirements evolve.

## Configuration

Copy `.env.example` to `.env` and provide the required configuration:

```env
POSTGRES_USER=postgres
POSTGRES_PASSWORD=your_password
POSTGRES_DB=physicalai
POSTGRES_HOST=localhost
POSTGRES_PORT=5432

KAFKA_BOOTSTRAP_SERVERS=localhost:9092
KAFKA_TOPIC=robot-events
```

When running through Docker Compose, the API and consumer use the Docker service names for PostgreSQL and Kafka.

> **Note:** `.env` is excluded from version control. Use `.env.example` as the template for required environment variables.

## Running with Docker

Build and start the services:

```bash
docker compose up --build
```

Run in detached mode:

```bash
docker compose up -d --build
```

Check service status:

```bash
docker compose ps
```

View logs:

```bash
docker compose logs -f
```

## Local Development (without Docker)

For working on the codebase or running tests without starting the full Kafka + PostgreSQL stack each time:

```bash
python -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate

pip install -r requirements.txt
pytest -v
```

Kafka and PostgreSQL still need to be reachable (either running locally or via `docker compose up postgres kafka`) for the API and consumer to function outside of tests.

## Testing

Run the test suite with:

```bash
python -m pytest -v
```

The project includes tests for:

* Telemetry API behavior
* Kafka consumer persistence
* Successful offset commits
* Offset behavior when database persistence fails

Tests are also executed automatically through GitHub Actions.
